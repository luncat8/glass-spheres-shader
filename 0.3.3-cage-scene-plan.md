# Plan — "cage" scene: pastel clouds + wireframe cube + bouncing balls

## Goal

Add a new shader `cage` that renders a self-contained scene:

- **Background**: procedural pastel cloud sky (no iChannel, no glsl_lib change).
- **Wireframe AABB cage** with front-face depth (bubbles in front of the entry face draw on top, bubbles behind are occluded).
- **Inside the cage**: 1...61 (GUI slider) glass bubbles (different sizes) reflecting off the 6 walls under Newtonian physics (constant velocity, elastic reflection off the wall normal, no gravity, no friction). Positions are analytic closed-form per `time`, deterministic and `mov:off`-freezable. **Bubbles do not collide and do not push each other** — each bubble moves on its own constant-velocity trajectory and only the AABB walls reflect it; bubbles can interpenetrate visually. This is intentional and is the natural consequence of the closed-form physics (no integration step, no collision response).
- **On top of the cage**: 3 balls that bounce on the top face under constant gravity (no friction), analytic closed-form. The top balls also do not collide with each other.

Uses the existing JS orbit camera, `mov` toggle, `aa` toggle, and click-select.

## Shader prelude (cage.js)

The cage shader's trace is a hybrid of `hollow_bubbles` (membrane tracing) and a custom top-ball / cage pass. The shared `GLSL.common` / `GLSL.raySphere` / `GLSL.camera` / `GLSL.selGlow` snippets cover most needs. **`GLSL.env` is NOT included** because it references `uScene` (which the cage shader doesn't expose) and defines an `env()` dispatcher we don't want.

What the cage shader needs from `GLSL.env`:
- `swirl(p)` — copy the 5-line definition locally.
- `envSun(d)` — define locally to return `pastelSky(d) + sun_term(d)`.

What the cage shader copies from `hollow_bubbles.js`:
- `tintOf(i)`, `filmTint(d)`, `crossWall(...)` — verbatim. They only depend on `swirl`, `envSun`, and the standard `GLSL.common` helpers.

### Pipeline (locked stack order)

1. Compute `bx = rayBox(ro, rd, vec3(uCageSize*uSpread))`. `tMax = bx.y` (or `BIG` on miss); `tFront = max(bx.x, 0)` for the wireframe.
2. **Inside bubbles** — same membrane loop as `hollow_bubbles.js:149-170`, bounded by `tMax`. With up to 61 bubbles the per-pixel inner loop is still O(`uCount`) for the membrane hit search; this is fine because `uLayers` (default 6) caps the wall crossings per pixel. (See Risks.)
3. **Background sky** — same 3-wavelength split as `hollow_bubbles.js:175-181`, calling the local `pastelSky()` instead of `envSun()`.
4. **Top balls** — for each, analytic ray-sphere; if hit, shade via local `shadeTopBall()` and `mix(col, bub, 0.85)`. No inter-ball collision or repulsion.
5. **Front-face cage wireframe** — draw the 12 edges at the entry t; mix to black with `cageWire()`.

The final pipeline is identical in structure to `hollow_bubbles.mainImage` — same uAA path, same `selGlow` + `tonemap` tail.

## Feed math (js/scene.js)

Per-frame feeds must not allocate (AGENTS.md). Module-level `Float32Array` scratch is allocated once at script load.

### `cageInside` — Newtonian physics: constant velocity, elastic reflection off AABB walls (closed form, up to 61 spheres)

**Physics rule** (as confirmed by the user: "spheres move and reflect from walls of the box", "Newtonian physics"):

- Each sphere has a fixed initial position `p0` and a fixed initial velocity `v = (vx, vy, vz)`.
- At any time `t`, the position is `p0 + v * t`, until the sphere's bounding sphere contacts one of the 6 inner faces of the AABB. The collision normal of that face is one of `(±1, 0, 0)`, `(0, ±1, 0)`, `(0, 0, ±1)`.
- On contact: the velocity component along the wall normal flips (`v_n → -v_n`); tangential components are unchanged. This is the standard elastic-reflection rule for a particle striking a flat wall (Newton's law of restitution with `e = 1`).
- No gravity, no friction, no sphere–sphere forces.

For an axis-aligned bounding box, the 6 wall normals are decoupled per axis, so the reflection rule reduces to: on each axis independently, when the position would cross `+B` or `-B`, that axis's velocity component flips sign. The result is a 1D bouncing motion along each axis — and combining three independent 1D bouncing motions along orthogonal axes is *exactly* 3D Newtonian motion inside an AABB. (For an *oriented* cube the wall normals would mix axes and you would need full 3D vector reflection; that is not the case here.)

**Closed form.** Because the velocity is constant between contacts and reflections only flip the sign of one component, the motion is piecewise linear. The closed form is the analytic expression of "linear motion, flip component on wall contact" — no per-frame integration, no state:

```
q   = p0 + v * time                              // unbounded linear motion
s   = ((q + B) mod 4B)                           // sawtooth in [0, 4B)
pos = (s < 2B) ? (s - B) : (3B - s)              // reflected position in [-B, +B]
```

Where `B = effectiveCAGE - radius * uSize` and `effectiveCAGE = uCageSize * uSpread` (both read from `meta` per frame so the scene stays self-consistent when the user moves the sliders). `radius * uSize` accounts for the sphere's bounding sphere; the sphere's centre must stay within `[-(B), +B]` so the sphere itself stays inside `[-(effectiveCAGE), +effectiveCAGE]`.

Verified trace: at `q = 0` we get `pos = 0` (sphere at initial position); at `q = 2B` we hit `pos = +B` (right wall, sign flip on `v_x`); at `q = 4B` we hit `pos = -B` (left wall, sign flip on `v_x` again); period `4B/|v|`. This is the analytic closed form of constant-velocity motion with elastic reflection off a flat wall.

**No inter-bubble forces.** Each sphere is computed independently from its own `(p0, v, r)` and the current `time`. They pass through each other visually — this is intentional and matches the user's "do not collide, do not push each other" rule. The visual reads as bubbles that bounce off the cube walls but not off each other.

**Reference**: this matches the standard "elastic impact with plane" rule (impulse orthogonal to the wall, `e = 1`, no friction) — see e.g. the GamePhysics lecture notes (tarini.di.unimi.it, *Collision Handling*) and the 3D collision-detection summary on MDN. For an AABB specifically, the wall normals are axis-aligned so per-axis 1D reflections compose to full 3D reflection; this is the standard simplification used by AABB physics engines.

### Scratch state (61 spheres, generated once at load)

```
CAGE_INSIDE: N=61, p0[N*3], v0[N*3], r[N]
```

Generated deterministically from a golden-angle / hash scheme (mirroring the cloud generator in `scene.js:21-43`) so that:
- Sphere i has a unique `(p0, v, r)`.
- Any contiguous prefix (e.g. first 14) looks like a coherent scene at that density.
- All spheres' per-axis velocity components are incommensurate so the motion never visibly synchronises — each axis of each sphere has a velocity component that doesn't share a rational ratio with any other.

The recommended generator (mirrors `scene.js:21-43`):
- `r[i] = (0.18 + 0.30 * Math.abs(Math.sin(GA * i * 2.1))) * sizeJitter` where `sizeJitter = 1 / Math.sqrt(N / 32)`.
- `p0[i*3+k]` sampled via `0.5 * Math.cos(GA * i * f_k) * (effectiveCAGE - r[i])` with three different `f_k` per axis.
- `v[i*3+k]` sampled via `0.4 + 0.6 * Math.abs(Math.sin(GA * i * g_k + seed_k))` for three different `g_k` per axis, sign chosen by golden-angle hash so half move each way. The sign of each velocity component must be independently random — not coupled across axes — so the spheres move in genuinely random 3D directions rather than along diagonals.

The feed is bounded by `Math.min(N, out.length >> 2)` so the shader can declare any count.

### `cageTop` — Newtonian physics: constant horizontal velocity, vertical bounce under gravity (closed form, 3 balls)

Per ball: `(x, z)` move with constant velocity `(vx, vz)` (no friction). The vertical axis `y` experiences constant gravity `g` and bounces elastically off the top face `y = effectiveCAGE` (and only the top — there is no floor; the ball drops back through `y = effectiveCAGE` after each apex).

**Physics rule**:
- Horizontal: `x = x0 + vx * t`, `z = z0 + vz * t`.
- Vertical: piecewise parabolic motion. While `y > effectiveCAGE`, `y = effectiveCAGE + v0y * (t - t0) - 0.5 * g * (t - t0)^2` where `t0` is the time of the last bounce. On each apex, `vy` flips sign (`vy → -vy`), then the ball falls back to `y = effectiveCAGE` and bounces again.

**Closed form** for the vertical position (no per-frame integration):

```
period = 2 * v0y / g
tp     = (((time + phase) mod period) + period) mod period
tUp    = v0y / g
y = tp < tUp
    ? effectiveCAGE + v0y * tp - 0.5 * g * tp^2
    : effectiveCAGE + v0y * tUp - 0.5 * g * tUp^2 - 0.5 * g * (tp - tUp)^2
```

`g` is read from `meta.uGravity` per frame, clamped to a small positive minimum. `effectiveCAGE = uCageSize * uSpread`. The `+ phase` term per-ball staggers their bounces so they don't synchronise.

The two branches meet at the apex (`tp == tUp`) with the same value `y = effectiveCAGE + v0y^2 / (2g)`, so the motion is continuous.

**Balls do not collide with each other** — each ball's motion is independent. This is consistent with the user's "no push" rule.

## Risks / open items

- **Camera inside the cube** (zoomed in past the wireframe): the front-face wireframe logic uses `max(bx.x, 0)` as the entry t. With `bx.x < 0`, the line distance is computed from the camera, which doesn't depth-order the visible edges against each other. The default orbit distance (`7.5`) and cage half-size (`4`) keep the camera outside by default, so this only matters if the user zooms way in. Acceptable: document as a known limitation.
- **Per-pixel cost at `uCount = 61`**: the membrane loop's inner search walks up to `uCount` spheres per wall crossing, with up to `uLayers` wall crossings per pixel. Default `uLayers = 6` gives at most `6 × 61 = 366` sphere tests per pixel — comparable to `hollow_bubbles` (which uses `uCount` up to 32 with 6 layers = 192 tests) but ~2× heavier at full count. Acceptable on modern GPUs; users on low-end hardware can lower `uLayers`. The user-set `uCount` slider is bounded to 1..61 so the worst case is predictable.
- **Top balls drift off the cage top**: the (x, z) walk is unbounded. The visible cage top is `[-4, 4]^2`, so a ball at velocity 0.35 walks off in ~12 seconds. Mitigation: clamp x/z to `[-CAGE+r, CAGE-r]` with a wall reflection (mirrors the inside balls' formula) — this is a 3-line addition to the feed if it becomes a problem. Defer until visually verified.
- **Incommensurate per-axis velocity components** prevent visible synchronisation. The generator signs each axis's velocity independently so spheres move in random 3D directions, not along diagonals.
- **`shadeTopBall` styling** is a styling detail deferred to implementation. The recommended recipe: Fresnel-weighted env reflection of the pastel sky + a small iridescent rim, no Beer-Lambert tint (balls are mostly opaque).
- **`GLSL.env` is not included** so the cage shader defines its own `swirl` and `envSun` shadows. If a future shader wants to share these, the right place to extract them is `GLSL.common` — out of scope here.
