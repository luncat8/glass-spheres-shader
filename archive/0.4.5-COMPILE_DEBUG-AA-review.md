## Short answer

**The AA claim is false for your current code — it was true of the *old* code and has already been fixed.** Your 4× cost is the **terrain scene**, not anti-aliasing. And the run‑1/run‑2 gap is just the driver cache, not a per‑launch cost.

---

## 1. What your numbers actually measure

`linkCall=0.0ms` and `compileWait≈20ms` in **both** runs. So `glLinkProgram` returns instantly (ANGLE defers everything) and the shader‑compile stage is cheap. 100% of your time is `linkWait/backend` — waiting for `COMPLETION_STATUS_KHR` to flip true. On ANGLE/D3D11 that stage is GLSL ES → HLSL translation, then **D3DCompile (fxc)**, then D3D shader‑object creation. That is single‑threaded **CPU** compiler work. Your RTX is irrelevant to it — a 3060, a 3090, or a 5090 all take the same time.

## 2. Run 1 vs run 2 = cache, not a real regression

Run 2 is 36–39 ms for **all six** variants. And in run 1, `t0:1` was 40 ms while its neighbours `t0:0`/`t0:2` were 852/1104 ms — that one exact source was already warm from an earlier session. Your page even says `Cold cache is NOT asserted`. This is a **one‑time cost per exact source**; you pay it once until a driver or Chrome update invalidates it.

## 3. I reproduced your exact source, then found the real 4× cause

I rebuilt all six variants with the repo's own assembler. **All six FNV‑1a hashes match yours** (`3336580a`, `627b5555`, `2e383f3c`, `d8a9aacb`, `88238d98`, `90d0cb21`), all `len=28824`. Same length because the *only* difference is two single digits — `#define USE_TERRAIN 0|1` and `#define SHAPE_MODE 0|1|2` ([js/runner.js:694](js/runner.js#L694)).

So `t1:*` = **terrain scene**. After preprocessing away the dead `#if` blocks:

| variant | real code | non-blank lines |
|---|---:|---:|
| `t0:0` sphere | 14,734 chars | 407 |
| `t0:2` tetra | 16,189 chars | 432 |
| `t1:0` sphere+terrain | **20,413 chars** | **569** |

And the terrain code is expansion‑heavy. `landHeight → fbm3 → 3× snoise`, called from 7 sites, one of which sits inside a **constant‑bounded** loop that the backend *will* unroll:

```
for (int i = 1; i <= n; i++)   -> DYNAMIC bound (stays a loop)   ✓ already safe
for (int j = 0; j < 4; j++)    -> CONSTANT bound (backend unrolls)  ✗
```

Worst case reachable from one `landHit()`: **27 copies** of the ~25‑line simplex function (4 unrolled bisection + 1 probe + 4 from `landNormal`, × 3 `snoise` each). That is your 4×.

## 4. The AA question — three different "AA"s

| | what it is | touches `analytic_layers` source? | link cost |
|---|---|---|---|
| **MSAA** | `antialias: true` context attr | no | none — and it's `false` everywhere (runner.js:598, compile_debug.js:291), your dump confirms |
| **SMAA** | the "global AA" button (js/smaa.js, 3 tiny programs at `SMAA.init`) | **no** | milliseconds, unrelated shaders |
| **`uAA`** | shader's own 2×2 supersampling | yes — but as a **uniform** | see below |

On the current `t1:0` source, `uAA` appears exactly **2 times**: `uniform float uAA;` (line 33) and `int samples = uAA > 0.5 ? 4 : 1;` (line 780). **Zero `#define uAA`.** A uniform can't fork a preprocessor path. `trace()` has exactly **one** call site (line 784) inside a uniform‑bounded loop, which the backend cannot unroll.

I then ran the decisive experiment — physically delete the AA and diff what the compiler would receive:

```
              with shader AA      AA physically removed   delta
  len             28824                 28610                   -214
  traceCalls      1                     1                       0
  traceDefs       1                     1                       0
  snoiseCalls     4                     4                       0
  landHeightCalls 8                     8                       0
```

Identical for `terrain=0`. **Removing AA changes 214 of 28,824 characters (0.7%) and changes the number of scene copies the backend must compile from 1 to 1.**

So: **no, removing AA will not speed up linking.** The person who told you about "path forks" was describing the pre‑fix code — [COMPILE_DEBUG.md](COMPILE_DEBUG.md) lines 29–32 document that exact 5× expansion, and lines 57–58 record the fix that removed it. Both statements were true, of different revisions.

## 5. What would actually help

Attack the terrain path, not AA: make the `for (int j = 0; j < 4; j++)` bisection runtime‑bounded the way the outer loop already is, and cut `landNormal`'s 4 `landHeight` calls (reuse samples, or a 2‑tap normal). That targets the 27 `snoise` copies directly. The ~0.9 s `t0` baseline is just fxc on a 15 KB fragment shader — nothing structural left there.

Also worth knowing: in the real app only the variant you actually view is compiled lazily ([js/runner.js:745](js/runner.js#L745) reuses `Runner.variants[key]`), so you don't pay 6 cold compiles — `debug.html`'s "compile all variants" button does that artificially.
