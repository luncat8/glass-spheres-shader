# Plan 0.4.2 — viewport-relative "grab" orbit camera

## Goal

Replace the constant-pixel-sensitivity drag orbit with viewport-relative *grab*
behaviour, and stop `js/camera.js` from touching shaders that do not consume the
shared camera. Three fixes, one discriminator:

1. **sensitivity** — one pixel of drag must mean the same fraction of a turn on a
   960 px window, a 4K display and any `devicePixelRatio`.
2. **direction** — dragging must move the scene with the cursor (grab), not
   against it (push), matching three.js `OrbitControls` and every "grab the
   world" viewer (Google Earth, model inspectors).
3. **ownership** — orbit, zoom, pick and auto-spin must only run for shaders that
   actually read the shared camera basis; everything else only forwards `iMouse`.

## Current state

| shaders | `group` | camera | declares `uCamPos` in `vars` |
|---|---|---|---|
| `XdXXzB`, `ld3SDl`, `llsSDf` | `orig` | own orbit from `iMouse`, inside GLSL | no |
| `multi_fresnel`, `multi_thinfilm`, `thick_glass` | `own` | own orbit from `iMouse`, inside GLSL: `doCamera` in `multi_thinfilm`, an inline `mo = PI * iMouse.xy / iResolution.xy` yaw/pitch in the other two | no |
| `hollow_bubbles`, `analytic_layers`, `thick_analytic`, `thick_chain`, `thick_raymarch` | `scene` | shared: `GLSL.camera` reads `uCamPos/uCamRt/uCamUp/uCamFw`, pick via `uSel` | **yes** |

`js/bench.js` entries (`bench_fresnel`, …) also declare `uCamPos`, but they
register as `window.BENCH_*`, not `window.SHADER_*`, so `js/shaders.js` never
collects them and they are not reachable from the main runner; the bench builds
its own fixed basis. They are unaffected by this plan.

Today `js/camera.js` applies one code path to all of them:

```javascript
Cam.yaw -= dx * 0.006;
Cam.pitch = clamp (Cam.pitch - dy * 0.005, -PITCH_MAX, PITCH_MAX);
```

Consequences: sensitivity scales with raw CSS pixels (a 4K window orbits ~4×
faster than a 960 px one for the same physical drag), yaw is inverted relative
to the grab convention, and orbit state / picking / auto-spin are computed for
shaders that never read them.

## Decision — one discriminator

A shader uses the shared camera **iff its metadata declares `uCamPos` in
`vars`**. That is exactly the contract the runner already uses to upload the
basis feeds, so it cannot drift out of sync with what the GLSL consumes.
`group` is *not* used: it describes scene compatibility, not camera plumbing.

The test is a metadata scan, so it is evaluated once per selected shader and
memoised on the meta object identity (pointer compare per event, no scan, no
allocation). Everything shared-camera-only then sits behind one early return per
handler — no per-statement `if` sprinkles:

```javascript
let sharedMeta, sharedFlag = false;

function declaresCamPos (meta) {
	const vs = (meta && meta.vars) || [];
	for (let i = 0; i < vs.length; i++) if (vs[i].name === 'uCamPos') return true;
	return false;
}

function sharedCam () {
	const meta = runner ? runner.current : undefined;
	if (meta !== sharedMeta) { sharedMeta = meta; sharedFlag = declaresCamPos (meta); }
	return sharedFlag;
}
```

| handler | legacy shader (`iMouse` in GLSL) | shared-camera shader |
|---|---|---|
| `onMove` | forwards `iMouse` only, then returns | orbit / pinch |
| `onUp` | no pick | pick on a click that never became a drag |
| `onWheel` | `preventDefault` only | zoom |
| `tick` | returns immediately | auto-orbit, selection follow, `basis()` |
| `cam` toolbar button | disabled, label `cam: n/a` | cycles auto / on / off |

`Runner.mouse` keeps being written unconditionally at the top of `onMove` — the
legacy GLSL cameras are driven by it and by `js/runner.js`'s own mouse
listeners, and they must keep working on touch.

## Drag math

```javascript
const ORBIT_TURN = Math.PI;      // one min-dimension of drag = 180°
const CLICK_MIN = 6.0;           // click-vs-drag threshold floor, CSS px
const CLICK_FRAC = 0.01;         // ... and its viewport-relative part
```

Both axes are normalised by **`min(clientWidth, clientHeight)`**, not by width
for yaw and height for pitch:

* viewport-relative — CSS pixels, so `devicePixelRatio` and canvas backing size
  are irrelevant, and the same physical drag gives the same turn at any window
  size;
* isotropic — a diagonal drag rotates as much as either axis alone, which
  per-axis normalisation breaks on any non-square viewport (on 16:9 it would
  make yaw ~1.8× slower than pitch);
* the min dimension is the one the pointer can always travel fully, so the turn
  rate stays bounded on letterbox / ultrawide viewports.

```javascript
const dim = viewDim ();                       // min(w, h), 0 when hidden
if (dim <= 0) return;
Cam.yaw   += (dx / dim) * ORBIT_TURN;
Cam.pitch  = clamp (Cam.pitch - (dy / dim) * ORBIT_TURN, -PITCH_MAX, PITCH_MAX);
```

`viewDim()` returns 0 for a zero-sized or hidden canvas, which makes the guard
fall out for free instead of dividing by zero.

### Sign convention (why `+dx`)

`basis()` places the eye at `pos = target - fw * dist` with
`fw = (sin yaw · cos pitch, sin pitch, cos yaw · cos pitch)`, so increasing
`yaw` moves the eye towards `-X` while the screen-right vector
`rt = (fw.z, 0, -fw.x)` keeps pointing along `+X` at `yaw = 0`.

* drag right (`dx > 0`) → `yaw` increases → eye orbits to `-X` → the surface
  under the cursor travels right → **grab**.
* drag down (`dy > 0`) → `pitch` decreases → `pos.y` rises → the eye looks down
  from above → the scene travels down → **grab**.

This is the same convention as three.js `OrbitControls`
(`sphericalDelta.theta -= 2π · dx / clientHeight`), whose spherical azimuth is
this rig's `yaw + π`. The pitch sign is unchanged from the legacy code, which
was already grab-correct; only yaw flips.

Turn rate at `ORBIT_TURN = π` on a 16:9 viewport: full-height drag = 180°,
full-width drag = 320°. That is ~2× slower than the legacy 0.006 rad/px on the
same window, which is intended — grab orbits are steered with short drags.

### Click-vs-drag threshold

`CLICK_DRAG = 6.0` px is hair-trigger on a 4K canvas and too coarse on a phone,
so it scales with the same reference dimension and keeps a floor:

```javascript
function clickDrag (dim) { return Math.max (CLICK_MIN, dim * CLICK_FRAC); }
```

1080p → 10.8 px, 4K → 21.6 px, 360 px phone → 6 px floor.

### Coordinates

`offsetX` / `offsetY` (canvas-relative CSS pixels) replace
`getBoundingClientRect()` in `onMove` and `pick()`: the listeners are on the
canvas itself, so the values are identical, and it removes a `DOMRect`
allocation from a handler that fires far more often than once per frame.
`Cam.pick(x, y)` therefore takes canvas-relative CSS pixels.

## Changes

| File | Change |
|---|---|
| `js/camera.js` | `sharedCam()` memoised discriminator; early returns in `onMove` / `onWheel` / `pick` / `tick`; viewport-relative isotropic grab math with `ORBIT_TURN`; scaling click threshold; `offsetX/offsetY`; unused `TAU` and unused `elapsed` argument dropped; `AUTO_PITCH` named; `modeLabel()` reports `cam: n/a`; `shared()` exported |
| `js/runner.js` | `Cam.tick(dt, elapsed)` → `Cam.tick(dt)` (the second argument was never read) |
| `js/ui.js` | `cam` button disabled + explanatory tooltip when the selected shader has no shared camera |
| `index.html` | `cam` tooltip says the shared orbit camera applies to the scene-aware shaders and that drag grabs the scene; `#bar #cam:disabled` rule, because two ids outrank the generic `#bar button:disabled` grey |

No shader, feed, scene or GLSL change: `basis()` produces the same vectors, only
when they change and how fast they change is different. Selection handling needs
nothing either — `attach()` already drops the selection on every shader and
scene switch, so `uSel.w` is 0 whenever a shared-camera shader is left.

## Out of scope

* Migrating `group: 'own'` shaders (`multi_fresnel`, `multi_thinfilm`,
  `thick_glass`) or the Shadertoy ports to the shared camera. They orbit inside
  GLSL from `iMouse`; that is a separate task.
* Changing the auto-orbit speed, the auto pitch target, `PITCH_MAX`, the zoom
  range or the zoom curve.
* Sensitivity sliders, per-user configuration, drag inertia, keyboard orbit.
* Making the legacy shaders' internal cameras feel like grab: only their
  `iMouse` stream is forwarded, unchanged.

## Validation

Two headless harnesses in `tools_GPU/` (dev-only and gitignored, like the rest of
the tooling; `npm install jsdom` for the second one). Both run without a browser
and without a GPU.

**`check-camera.mjs` — unit.** `js/camera.js` returns early under node, so the
file is executed in a `node:vm` sandbox providing the browser bits it touches: a
canvas stub that records its own listeners, a runner stub and stub sphere feeds.
The recorded handlers are driven with synthetic pointer / wheel events.

* drag right by `dim/2` → `yaw` exactly `+π/2`; drag up by `dim/4` → `pitch`
  exactly `+π/4`; after `tick(0)`, `Feeds.camPos` reports an eye with
  `pos.x < 0` — the eye orbited towards `-X`, i.e. the scene followed the cursor.
* the same *fractional* drag on 960×540, 1920×1080, 3840×2160 and 2560×1080 at
  different `devicePixelRatio` gives byte-identical `yaw` / `pitch` deltas.
* `pitch` saturates at `±PITCH_MAX` on an over-long drag; `yaw` keeps winding;
  nothing becomes NaN.
* a 0×0 canvas skips the viewport-relative math (no orbit, no pick) and leaves
  every value finite — wheel zoom is size-independent and keeps working.
* a legacy meta (`vars` without `uCamPos`) leaves `yaw`, `pitch`, `dist` and
  `sel` untouched for drag, wheel, pinch, click and `tick`, while
  `runner.mouse` still receives device-pixel coordinates; `label()` says
  `cam: n/a` and `shared()` is false.
* a shared meta picks the bubble under a click (`sel.w > 0`, orbit target follows
  it) and clears it on a click that misses; a drag never picks; clicking again
  after a drag still picks.
* `tick(dt)` in auto mode advances `yaw` by `AUTO_SPEED · dt`, a manual drag
  turns auto off, and `off` never advances.
* the discriminator follows the selected shader in both directions.
* RMB drags and moves without a press are ignored.

**`check-ui.mjs` — integration.** The real `index.html` runs in jsdom with a
proxied WebGL2 context (every call a no-op, `create*` returns a handle,
compile/link/framebuffer queries succeed), so the real `runner.js`, `scenes.js`,
`ui.js` and `camera.js` wire-up is exercised:

* all 11 selectable shaders pick without an error and become `Runner.current`;
* for each of them, `Cam.shared()`, the `cam` button's `disabled` state and its
  label agree with whether the shader declares `uCamPos` — the five scene-aware
  shaders (`hollow_bubbles`, `thick_raymarch`, `thick_chain`, `analytic_layers`,
  `thick_analytic`) stay enabled, the six own-camera shaders (`XdXXzB`,
  `llsSDf`, `ld3SDl`, `multi_fresnel`, `multi_thinfilm`, `thick_glass`) read
  `cam: n/a` and are disabled with a tooltip that says why;
* a pointer drag dispatched on the real canvas element turns the five shared
  shaders by the exact viewport-relative amount and leaves the six others
  unmoved;
* every scene still applies to a scene-aware shader and the parameter strip is
  still populated.

Plus `node --check` on every changed file and a browser pass: the five
scene-aware shaders orbit with grab drag at the same feel in a 960 px window and
on a 4K display, zoom (wheel + pinch) and pick; the six own-camera shaders keep
their GLSL `iMouse` orbit on mouse and touch.
