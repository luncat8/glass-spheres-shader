# Report 0.3.3 — cage scene: what was built and what changed

> This is the **implementation report** for the cage scene: it records what
> shipped and how it differs from the first draft of the plan.
> The prescriptive document is `archive/0.3.3-cage-scene-plan.md` — read that one
> to fork or re-create the scene. The first draft of the plan is preserved in git
> history at commit `0b7d288`.
>
> Note: version 0.3.4 later split shader selection from scene selection and
> renamed the standalone `cage` renderer to `analytic_layers`. File and id names
> below are the ones that were current in 0.3.3.

## Goal

Add a `cage` scene with:

- smooth procedural pastel clouds behind the scene;
- a black, twelve-edge wire cube;
- independently moving spheres inside the cube, with constant velocity, no gravity, no friction, and perfectly elastic reflection from all six walls;
- three balls above the top face, each following a vertical gravity bounce with no friction;
- the existing orbit camera, movement freeze, global AA, parameter UI, and click selection.

Spheres do not collide with or push one another. Their trajectories may cross.

## Review of the draft

The original draft had the right overall decomposition, but several details were either incorrect or unnecessarily expensive:

1. **A ray-box entry point cannot render all twelve cage edges.** It only describes the first face crossed by a ray. The implementation tests the view ray against each finite cube edge instead. The closest ray/segment distance produces an antialiased line mask and its ray parameter provides depth, so front wires occlude spheres while rear wires remain behind them.
2. **The triangle-wave example was off by one half traversal.** For half-extent `B`, a particle starting at zero reaches `+B` when its unbounded coordinate reaches `B`, not `2B`. The fold used by the implementation is:

   ```text
   s   = positiveMod(q + B, 4B)
   pos = B - abs(s - 2B)
   ```

   It maps any linear trajectory into `[-B, B]` and exactly flips the normal velocity at either endpoint.
3. **A top ball's centre cannot touch `y = cage`.** That would put half the sphere through the top face. Contact is at `y = cage + radius`.
4. **Unbounded horizontal drift would make the top balls leave the cube quickly.** The requested motion is described as vertical bouncing, so the implementation gives those balls zero initial horizontal velocity. With no friction, zero horizontal velocity remains zero. Their distinct fixed `(x,z)` positions and phase offsets keep the motion readable.
5. **A copied hollow-membrane event loop is excessive at 61 spheres.** Six membrane crossings times 61 tests per crossing is expensive, and clipping a refracted ray against the original ray-box interval is not valid. The cage renderer instead finds the nearest three analytic sphere layers in one bounded pass. Inside spheres retain a lightweight glass/film appearance; top balls use a mostly opaque material.
6. **`uSpread` duplicated `uCageSize`.** One cage-size control and one radius-size control are sufficient and cannot disagree about what is being scaled.
7. **No texture channels are needed.** The sky is analytic, so `channels` is empty.
8. **The existing background selector is direction-only.** It cannot by itself express world-space cage lines or movement constraints. The implementation therefore has two layers: a full dedicated `cage` renderer, plus a shared pastel environment/wire/top-ball overlay used by every modern renderer that already exposes the scene selector. Their sphere positions come from the same cage feed. Legacy cubemap-only and 2D shaders have incompatible camera/material pipelines and are skipped, as allowed by the request.
9. **The existing click ray used CSS Y without converting to WebGL Y.** That mirrored picks vertically. Cage testing exposed it, so the pointer ray now flips Y and aligns with the sphere visible under the cursor in every camera-based shader.

  uInside vec4[61] <- cageInside
  uTop     vec4[3] <- cageTop
vars:
  shared orbit-camera basis and uSel

  uCount       1..61, default 14

  uGravity     top-ball gravity

The regular toolbar AA remains available and is independent from local supersampling.

## Compatibility mode

`hollow_bubbles`, `thick_analytic`, `thick_chain`, and `thick_raymarch` gain a fourth `scene` option named `cage`:

- `GLSL.env` supplies the same pastel cloud environment to each material, including its reflection and refraction rays;
- `GLSL.cageOverlay` supplies all twelve world-space lines and the three opaque top balls;
- `hollow_bubbles` reuses its existing array but switches that feed to reflected cage trajectories only while scene 3 is selected;
- the three former fixed-four renderers now consume a `sceneBubbles4` array feed. It exactly mirrors their original trajectories in scenes 0–2 and supplies the first four reflected trajectories in scene 3. As a useful side effect, their movement now obeys `mov: off`;
- each material keeps its own sphere shading. The shared top-ball material is deliberately simple and consistent.

The standalone renderer allows 61 spheres and more accurate sphere/wire layer ordering. Compatibility mode is intentionally limited to each renderer's native sphere count and overlays thin wires after its material pass, avoiding invasive changes to raymarch/refraction internals.

## Inside-sphere motion

Each sphere has setup-time constants:

```text
normalised initial position p0
world-space velocity v
base radius r
```

For each frame and axis:

```text
R = r * uSize
B = max(0.05, uCageSize - R)
q = p0 * B + v * sceneTime
s = positiveMod(q + B, 4B)
position = B - abs(s - 2B)
```

Properties:

- `position` always lies in `[-B,+B]`, so the complete sphere remains within the cube;
- motion between contacts is linear and constant-speed;
- only the velocity component normal to a contacted AABB wall changes sign;
- tangential components do not change;
- there is no frame-step integration, accumulated drift, gravity, friction, or sphere/sphere response;
- `sceneTime` is the runner's movement time, so `mov: off` freezes all physical motion exactly.

The initial conditions are generated once from deterministic golden-angle/hash values. Directions are distributed over a sphere and speeds are independently jittered to avoid synchronised or diagonal-looking paths. The per-frame feed writes directly to the runner-provided `Float32Array` and allocates nothing.

## Top-ball motion

Each top ball has a fixed horizontal point, base radius, launch velocity, and phase fraction. For gravity `g`:

```text
period = 2v / g
t = positiveMod(sceneTime + phase * period, period)
height = v*t - 0.5*g*t*t
y = uCageSize + radius + height
```

The same parabola covers ascent and descent and returns continuously to the contact plane at the end of every period. Distinct launch speeds and phases avoid synchronisation. Radius is included in the contact height.

## Rendering

For each camera ray:

1. Evaluate a low-frequency, three-octave trigonometric cloud field over the ray direction and blend a peach/blue/lilac pastel sky. Cloud drift uses visual `iTime`, so freezing physical motion does not freeze the atmosphere.
2. Test active inside and top spheres analytically, retaining the nearest three hits.
3. Compute closest approach to all twelve finite cube edges. Convert world distance to an antialiased black line mask and retain the nearest wire depth.
4. Composite retained sphere layers back-to-front, inserting the wire layer at its measured depth.
5. Shade inside spheres as lightweight transparent glass membranes with Fresnel reflection, absorption, and thin-film colour. Shade top balls as mostly opaque pastel material with a reflective/iridescent rim.
6. Add the selected-sphere green rim and tone-map.

The primary cost is one loop over at most 61 inside spheres, one loop over three top balls, and twelve edge tests per sample. All loops have compile-time upper bounds.

## Picking

On a click, `camera.js` refreshes the active inside feed (`cageInside`, `bubbles`, or `sceneBubbles4`) and `cageTop`, then copies only their active prefixes into one preallocated pick buffer. The regular nearest ray/sphere test covers inside and top spheres together. The saved selection records which source array and local index were chosen, allowing the selected centre and orbit target to follow that sphere without per-frame allocation.

Changing either count below the selected index clears selection safely.

## Validation

- Run `node --check` for every changed JavaScript file.
- Assemble and compile the exact WebGL2 fragment source where a GLSL-capable browser/tool is available.
- Confirm both feeds stay finite and every inside sphere satisfies `abs(center[axis]) + radius <= cageSize` over varied times, cage sizes, and radius scales.
- Confirm each top sphere reaches contact at `cageSize + radius`, never penetrates the face, and remains horizontally over the top square.
- Browser checks:
  - all twelve black edges are visible as the camera orbits;
  - front/rear edge depth relative to spheres is stable;
  - inside spheres reflect only from cube walls and pass through one another;
  - top balls bounce vertically with staggered phases;
  - `mov: off` freezes spheres but not cloud drift;
  - camera drag/zoom, global AA, sliders, and picking continue to work;
  - counts 1 and 61 both render without shader errors;
  - selecting cage in each of the four compatible material renderers changes its motion/background/overlay, while scenes 0–2 retain their prior appearance and trajectories.
