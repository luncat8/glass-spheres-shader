# Plan 0.3.3 — "cage" scene: pastel clouds + wireframe cube + bouncing balls

> Status: implemented. See `archive/0.3.3-cage-scene-report.md` for what actually
> shipped and how it differs from the first draft of this plan.
>
> This document is the *corrected* plan: the original draft is preserved in git
> history (`0b7d288`), and every item that review or implementation proved wrong
> has been fixed in place, with the reason recorded in
> [Review corrections](#review-corrections). Read this file if you want to
> re-create or fork the cage scene from scratch; read the report if you want the
> diff against the first draft.

## Goal

Add a `cage` scene that renders:

- **Background** — a smooth procedural pastel cloud sky. Analytic, direction-only,
  no `iChannel` texture, so it can also be used as the reflection/refraction
  environment of any glass material.
- **A black twelve-edge wire cube** with correct depth against the spheres:
  front wires occlude spheres, rear wires are occluded by them.
- **Inside the cube** — `1..61` (GUI slider) glass spheres of different sizes
  moving under Newtonian physics: constant velocity, elastic reflection off the
  six inner walls, no gravity, no friction. Positions are closed-form per `time`,
  deterministic, and freezable by `mov: off`.
- **On top of the cube** — three balls bouncing vertically on the top face under
  constant gravity, also closed-form.

Spheres **do not** collide with or push one another; trajectories may cross and
spheres may visually interpenetrate. This is intentional and is the natural
consequence of the closed-form physics (no integration step, no collision
response).

Reuses the existing JS orbit camera, `mov` freeze, global AA, parameter UI and
click-to-select.

## Locked decisions

| Decision | Choice |
|---|---|
| Inside-sphere look | Lightweight transparent glass: Fresnel reflection + Beer-Lambert absorption + thin-film colour |
| Inside count | `1..61`, GUI slider, default 14. Each sphere gets a unique deterministic `(p0, v, r)` so any prefix reads as a sample of the same scene |
| Inter-sphere interaction | **None.** No collision detection, no repulsion, no integration step |
| Top balls | 3, distinct sizes, distinct launch speeds and phases; mostly opaque with a reflective/iridescent rim |
| Top-ball horizontal motion | **Zero.** Each ball keeps a fixed `(x, z)` over the top face |
| Camera | Reuse the existing JS orbit camera (`js/camera.js`) |
| Cage depth | Twelve **finite ray/segment** tests, not a ray-box entry point |
| Pastel sky | Added to `GLSL.env` as theme 3 so every scene-aware renderer can share it |
| Click-pick | Extend `pickable()` in `js/camera.js` to merge the inside feed and the top feed into one pickable set |
| Sphere physics | Newtonian, restitution `e = 1`, no friction; per-axis closed-form triangle-wave fold |
| Top-ball physics | Newtonian, closed-form parabola, contact at `y = cage + radius` |
| Music | Out of scope (`meta.music` absent; the music checkbox stays disabled) |
| Bench variant | Out of scope (bench is for cross-shader perf, not one-off scenes) |

## Review corrections

These are the points where the first draft was wrong or unnecessarily expensive.
They are already folded into the sections below; they are listed here so a
re-implementation does not repeat them.

1. **A ray-box entry point cannot render all twelve cage edges.** It only
   describes the first face a ray crosses. Test the view ray against each finite
   cube edge instead: closest ray/segment distance gives an antialiased line
   mask, and its ray parameter gives depth, so front wires occlude spheres while
   rear wires stay behind them.
2. **The draft's triangle wave was off by half a traversal.** For half-extent
   `B`, a particle starting at zero reaches `+B` when its unbounded coordinate
   reaches `B`, not `2B`. Use the fold in
   [Inside-sphere motion](#inside-sphere-motion).
3. **A top ball's centre cannot touch `y = cage`.** That pushes half the sphere
   through the top face. Contact is at `y = cage + radius`.
4. **Unbounded horizontal drift makes the top balls leave the cube quickly.** The
   requested motion is a vertical bounce, so give those balls zero initial
   horizontal velocity. With no friction, zero stays zero — no clamping or extra
   wall reflection is needed. Distinct fixed `(x, z)` positions plus phase
   offsets keep the motion readable.
5. **A copied hollow-membrane event loop is too expensive at 61 spheres.** Six
   membrane crossings × 61 tests per crossing is a lot of work, and clipping a
   refracted ray against the original ray-box interval is not valid anyway. Find
   the nearest three analytic sphere layers in one bounded pass instead.
6. **`uSpread` duplicated `uCageSize`.** Keep one cage-size control and one
   radius-size control; two scale controls can disagree about what is scaled.
7. **No texture channels are needed.** The sky is analytic, so `channels` is
   empty for the dedicated renderer.
8. **The existing background selector is direction-only.** It cannot by itself
   express world-space cage lines or movement constraints, so the cage scene
   needs two layers: a dedicated renderer *and* a shared world-space overlay for
   the other scene-aware renderers (see
   [Two-layer structure](#two-layer-structure)).
9. **The existing click ray used CSS Y without converting to WebGL Y.** That
   mirrored every pick vertically. Flip Y in `pick()`; the cage scene is simply
   what exposed the bug.

## Two-layer structure

The cage is not only a background, so it cannot be a `GLSL.env` theme alone. Ship
two layers:

1. **A dedicated cage renderer** (`shaders/cage.js`) — 61 spheres, accurate
   sphere/wire layer ordering, its own glass material.
2. **A shared world-space overlay** (`GLSL.cageOverlay` in `js/glsl_lib.js`) —
   the twelve edges and the three opaque top balls, composed *after* a
   renderer's own material pass. Every renderer that already exposes the shared
   `scene` selector gets `cage` as a fourth option and keeps its own sphere
   shading.

Compatibility mode is deliberately limited to each renderer's native sphere
count and overlays thin wires after its material pass, which avoids invasive
changes to the raymarch/refraction internals.

Legacy cubemap-only and 2D shaders (`XdXXzB`, `llsSDf`, `ld3SDl`,
`multi_fresnel`, `multi_thinfilm`, `thick_glass`) have incompatible
camera/material pipelines and are skipped.

## Inside-sphere motion

Each sphere has three setup-time constants: a normalised initial position `p0`,
a world-space velocity `v`, and a base radius `r`.

Per frame, per axis:

```text
R   = r * uSize
B   = max (0.05, uCageSize - R)
q   = p0 * B + v * sceneTime          // unbounded linear motion
s   = positiveMod (q + B, 4B)         // sawtooth in [0, 4B)
pos = B - abs (s - 2B)                // folded into [-B, +B]
```

Verify the fold: `q = 0 -> pos = 0`; `q = B -> pos = +B` (contact with the `+`
wall); `q = 3B -> pos = -B`; period `4B / |v|`.

Properties:

- `pos` always lies in `[-B, +B]`, so the whole sphere stays inside the cube;
- motion between contacts is linear and constant-speed;
- only the velocity component normal to the contacted AABB wall changes sign,
  tangential components are untouched — which is exactly restitution `e = 1`
  with no friction, and for an *axis-aligned* box the three axes decouple, so
  three independent 1D bounces compose into full 3D reflection. (An *oriented*
  box would mix axes and need real vector reflection.)
- no frame-step integration, no accumulated drift, no gravity, no friction, no
  sphere/sphere response;
- `sceneTime` is the runner's movement time, so `mov: off` freezes the physics
  exactly, while `iTime`-driven effects (cloud drift, iridescence) keep running.

Generate the initial conditions once, deterministically, from golden-angle/hash
values. Distribute directions over a **sphere** and jitter speeds
**independently** — per-axis sign generators produce diagonal, synchronised-looking
paths. The per-frame feed writes straight into the runner-provided
`Float32Array` and allocates nothing.

## Top-ball motion

Each top ball has a fixed horizontal point, a base radius, a launch velocity and
a phase fraction. For gravity `g`:

```text
period = 2v / g
t      = positiveMod (sceneTime + phase * period, period)
height = max (0, v*t - 0.5*g*t*t)
y      = uCageSize + radius + height
```

One parabola covers ascent and descent and returns continuously to the contact
plane at the end of every period. Distinct launch speeds and phases prevent
synchronisation. The radius is part of the contact height (correction 3), and the
horizontal velocity is zero (correction 4), so no clamping is required.

## Rendering

For each camera ray:

1. Evaluate a low-frequency three-octave trigonometric cloud field over the ray
   direction and blend a peach/blue/lilac pastel sky. Cloud drift uses visual
   `iTime`, so freezing the physics does not freeze the atmosphere.
2. Test the active inside and top spheres analytically, retaining the nearest
   **three** hits (correction 5). Three transparent shells are enough to preserve
   overlap depth without multiplying work by layer count.
3. Compute closest approach to all twelve finite cube edges (correction 1).
   Convert world distance to an antialiased black line mask and keep the nearest
   wire depth. Widen the antialias band with distance so far wires do not alias.
4. Composite the retained sphere layers back-to-front, inserting the wire layer
   at its measured depth rather than as an always-on-top screen overlay.
5. Shade inside spheres as lightweight transparent glass membranes (Fresnel
   reflection, absorption, thin-film colour). Shade top balls as mostly opaque
   pastel material with a reflective/iridescent rim.
6. Add the selected-sphere green rim, then tone-map.

Cost per sample: one loop over at most 61 inside spheres, one loop over three top
balls, twelve edge tests. All loops have compile-time upper bounds, which keeps
the shader safe on integrated GPUs.

## Compatibility mode

`hollow_bubbles`, `thick_analytic`, `thick_chain` and `thick_raymarch` gain a
fourth `scene` option, `cage`:

- `GLSL.env` supplies the same pastel cloud environment to each material,
  including its reflection and refraction rays;
- `GLSL.cageOverlay` supplies the twelve world-space lines and the three opaque
  top balls, and is a no-op unless `uScene == 3`;
- `hollow_bubbles` keeps its existing `uBubbles` array but its feed switches to
  reflected cage trajectories while scene 3 is selected;
- the three former fixed-four renderers move from the GLSL-side `bubble(i, t)`
  helper to a `sceneBubbles4` array feed. It mirrors their original trajectories
  exactly in scenes 0–2 and supplies the first four reflected trajectories in
  scene 3. Useful side effect: their movement now obeys `mov: off`;
- each material keeps its own sphere shading; the shared top-ball material is
  deliberately simple and consistent across renderers.

## Picking

On a click, `camera.js` refreshes the active inside feed (`cageInside`,
`bubbles` or `sceneBubbles4`) plus `cageTop`, then copies only their **active
prefixes** into one preallocated pick buffer. The normal nearest ray/sphere test
then covers inside and top spheres together.

The saved selection records which source array and which local index were
chosen, so the selected centre and the orbit target can follow that sphere every
frame without allocating.

Lowering either count below the selected index clears the selection safely.

Fix the pointer ray while you are here (correction 9): CSS pointer Y grows
downward, `gl_FragCoord`/camera UV Y grows upward, so the ray must use
`uy = (1 - 2 * ry) * ...`.

## Validation

- `node --check` on every changed JavaScript file.
- Assemble and compile the exact WebGL2 fragment source where a GLSL-capable
  browser/tool is available.
- Assert both feeds stay finite and that every inside sphere satisfies
  `abs (center[axis]) + radius <= cageSize` over varied times, cage sizes and
  radius scales.
- Assert each top sphere reaches contact at exactly `cageSize + radius`, never
  penetrates the face, and stays horizontally over the top square.
- Browser checks:
  - all twelve black edges are visible as the camera orbits;
  - front/rear edge depth relative to the spheres is stable;
  - inside spheres reflect only off cube walls and pass through one another;
  - top balls bounce vertically with staggered phases;
  - `mov: off` freezes the spheres but not the cloud drift;
  - camera drag/zoom, global AA, sliders and picking keep working;
  - counts 1 and 61 both render without shader errors;
  - clicking a sphere or a top ball lights the green rim, and the rim tracks the
    sphere the cursor was actually over (Y-flip regression);
  - selecting `cage` in each of the four compatible renderers changes its
    motion/background/overlay, while scenes 0–2 keep their prior appearance and
    trajectories.

## Risks / known limitations

- **Camera inside the cube.** Zoomed past the wires, edge/sphere ordering is
  still correct (the segment test is depth-based, not entry-based), but the
  scene is no longer readable as a cage. Default orbit distance 7.5 vs default
  half-size 2.2 keeps the camera outside; documented, not guarded.
- **Cost at `uCount = 61`.** 61 sphere tests + 12 edge tests per sample. The
  nearest-three-layer design keeps this linear; lower `uCount` on weak hardware.
- **Compatibility mode is approximate.** The overlay draws wires *after* the
  material pass, so wires seen *through* a refracting bubble are not bent. The
  dedicated renderer is the accurate one.
- **Sphere/sphere interpenetration** is by design, not a bug.
